- 2026-10-20 S3.11: DECISION, CSRF token storage. The plan said to take `X-CSRF-Token` from the CSRF cookie. That cannot work: the API sets `nhc_csrf` as HttpOnly with path `/api/v1/auth`, so page script cannot read it (and cross-origin it never could). The header is made from the `csrf_token` in the login and refresh response body. That value is kept in `localStorage` (`nhc.csrf`) so a reload or a returning visit can still call refresh; the access token and the user stay in memory only. It is not a credential on its own (refresh also needs the HttpOnly refresh cookie), but script on the page can read it, so an XSS bug could call refresh. Alternative, backend change: a non-HttpOnly CSRF cookie readable from the page (same-site deployment only). Owner to decide; the storage lives in `features/admin/auth/authStore.ts` only.

Only a 401 or 403 from refresh signs the user out; a network or 5xx failure keeps a signed-in user and settles a first load on the login screen without deleting the stored token. `logout()` clears local state first, then calls `/auth/logout` best effort.
